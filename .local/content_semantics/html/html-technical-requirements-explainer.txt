Technical Requirements
Technical requirements separate the tools needed to read, validate, regenerate, render, retrieve, and refresh derivatives.
Summary of Technical Requirements
The technical requirements explainer describes the local runtime, package, validation, rendering, retrieval, and derivative-build requirements needed to inspect or regenerate project surfaces safely. Its function is to separate read-only inspection, Python validator execution, memory and wiki regeneration, governed Mermaid inline-SVG rendering, local Obsidian or semantic retrieval, and LaTeX/PDF refresh into distinct tiers. This matters because not every reader needs every tool, and optional operator aids such as Obsidian or global Codex plugins should not be mistaken for project authority. The requirements map turns setup files and skill contracts into a practical dependency model for maintainers who need repeatable validation without changing dependency policy or scientific claims.

Read and Inspect
README.md
AGENTS.md
The minimum tier is ordinary reading and inspection: a text editor, Git, shell access, and the ability to open Markdown, CSV, YAML, HTML, and TeX sources. This tier supports understanding but not full regeneration. A reader can inspect authority, source materials, and registries without installing every optional tool. That distinction matters because missing a diagram renderer or Obsidian app should not be mistaken for a failure of the repository’s source authority. This tier is enough for source review, issue triage, and conceptual orientation, but it is not enough to claim that generated outputs are fresh.

Memory regeneration uses project-memory-system scripts to refresh format registries, generated wiki notes, file object rows, content semantics, local vault entries, folder maps, and query surfaces. It is required when source or registry changes affect generated memory. The tier exists because generated retrieval is useful only when it tracks source state. A stale derivative should trigger regeneration and validation, not manual edits to the generated note.

Diagram-backed HTML requires the governed Mermaid rendering tier: Node.js, npm, the pinned Mermaid package, Playwright Chromium when rendering is needed, inline SVG generation at build time, and source parity checks. The project avoids runtime Mermaid imports in tracked HTML so pages remain portable and no-network. Diagram tooling is therefore a project requirement only for regenerating diagram-backed HTML, not for merely reading source Markdown.
Local Retrieval
.codex/skills/obsidian-wiki/SKILL.md
.codex/skills/project-memory-system/SKILL.md
Local retrieval tools such as Obsidian, SQLite query helpers, semantic extracts, browser previews, and `.local` scratch surfaces are operator aids. They can make review faster, especially in a large research repository, but they do not become project authority. If a local tool is missing, the repository can still be valid; if a local view is stale, regenerate it from tracked sources. The operator can use these aids for speed, then return to source files, registries, and validator output when making a project claim.
PDF Refresh

The PDF tier is conditional. LaTeX or a managed TeX runtime is needed when refreshing human-reading PDF derivatives from registered TeX sources. PDFs are useful for review and distribution, but the canonical scientific source remains TeX. A PDF refresh should update derivative files and registry hashes while preserving the rule that PDF convenience does not outrank source text. If the TeX source changes but the PDF does not, the PDF should be treated as stale derivative evidence until the build and registry refresh succeed.
Requirement Boundary
README.md
AGENTS.md
The boundary separates project requirements from operator conveniences. Python validators, memory bootstrap, registered renderer tooling, and required tests are project requirements when their lane is in scope. Obsidian, global Codex plugins, editor extensions, personal browser state, and local previews are operator aids unless explicitly mirrored into repository contracts. This distinction keeps setup guidance practical without letting the local machine redefine project validity. The boundary also helps troubleshoot failures: missing project requirements block validation, while missing conveniences usually only reduce ergonomics.
