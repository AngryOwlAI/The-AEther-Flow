Research-Control System
The research-control system governs changes to the project itself: roles, skills, validators, documentation, generated derivatives, and checkpoint boundaries.
Summary of Research-Control System
The research-control system is the repository’s governance layer for deciding how project-system and research-continuation work may proceed. Its function is to classify changes, resolve advisory routing, create or reuse one bounded AgentJob, enforce role and write-path boundaries, require documentation-impact receipts when project machinery changes, and validate that source specs, skills, roles, registries, claim boundaries, optional parent-child decomposition evidence, teaching Q&A packets, and generated derivatives remain aligned. It matters because AEther-Flow deliberately combines scientific exploration with agent workflow development. Without control records, generated HTML, GitHub-facing Markdown, teaching packets, validators, and role contracts could drift or be mistaken for scientific authority. The system makes improvements reversible, auditable, and separate from physics claim promotion.

Classification and Resolver
AGENTS.md
.codex/skills/improve-project-system/SKILL.md
scripts/project_control/classify_project_changes.py
Project-system work starts with classification. The classifier reports whether current changes affect documentation, registries, control contracts, generated derivatives, validators, tests, memory tooling, or blocked paths. The resolver then provides advisory routing based on current Git state and registered project-improvement signals. Advisory does not mean optional chaos: it identifies the relevant authority surfaces, but hard checkpoint gates remain validators and concrete boundary violations. This separation lets a user-authorized improvement proceed while still recording why the selected role and scope are legitimate.
Bounded Transaction
.agents/schemas/AGENT_JOB_SCHEMA.md
research_control/README.md
The transaction boundary is one AgentJob. It names the objective, selected role, allowed reads, allowed writes, generated paths, forbidden paths, validators, expected outputs, human-gate status, documentation-impact record, and completion record. For project-system work, this prevents “improve the docs” or “fix the system” from becoming an unlimited rewrite. A transaction can include generated derivatives only when the source spec or contract authorizes regeneration, and it must stop when a required write path or policy decision exceeds the boundary.

Documentation Impact
scripts/project_control/validate_documentation_impact.py
research_control/README.md
Documentation impact is the receipt that connects a change to its documentation surface. It records changed paths, reason codes, source surfaces inspected, source docs updated, generated derivatives, registries, validators run, and status. The receipt does not decide routing by itself; it proves that a project-system transaction accounted for the documentation consequences of the actual change. A valid no-op rationale is allowed only when source documentation truly did not need updates.
Validator Chain
scripts/research_control/validate_research_control.py
scripts/spec_depth_lint.py
scripts/validate_teaching_qa.py
The validator chain combines hard and advisory checks. Teaching Q&A validation confirms packets are source-bound and noncanonical. Depth lint checks finished documentation quality, including the new self-reference guard. Bootstrap refreshes registries, wiki notes, hashes, and source-basis metadata. Documentation-impact validation checks receipts. Research-control validation checks tasks, jobs, roles, completions, claim boundaries, and diff constraints. A checkpoint should happen only after these gates agree that the transaction stayed inside its declared boundary.
