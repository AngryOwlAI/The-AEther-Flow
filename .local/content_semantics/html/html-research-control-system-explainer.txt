Summary of Research-Control System
The research-control system is the repository's governance layer for deciding how project-system and research-continuation work may proceed. Its function is to classify changes, resolve advisory routing, create or reuse one bounded AgentJob, enforce role and write-path boundaries, require documentation-impact receipts when project machinery changes, and validate that source specs, skills, roles, registries, claim boundaries, optional parent-child decomposition evidence, teaching Q&A packets, and generated derivatives remain aligned. It blocks PASS completions when a parent-child synthesis lacks a fused output or leaves a blocking conflict unresolved, and it requires teaching-enabled documentation to keep Student and Teacher material source-bound and noncanonical. It matters because the project deliberately combines scientific exploration with agent workflow development; without control records, generated HTML, GitHub-facing Markdown, teaching packets, validators, and role contracts could drift or be mistaken for scientific authority. The system fits the larger project by making improvements reversible, auditable, and separate from physics claim promotion.

The classifier and resolver separate observed Git changes from advisory routing state. Documentation drift can route to Documentation Curator, while role, schema, validator, workflow-command, or routing-contract drift routes elsewhere. That distinction matters because documentation-impact evidence is a receipt requirement, not by itself proof that a Documentation Curator job is sufficient. The resolver helps select a role boundary and identify open project-improvement signals, but it is advisory. Hard checkpoint gates remain validator failures, explicit authority-boundary violations, missing required receipts, or write paths outside the AgentJob allowlist. A reader should therefore treat classifier and resolver output as routing evidence to inspect, not as a replacement for the task contract.

One bounded AgentJob is the accountable unit of work. It names reads, writes, generated paths, forbidden paths, validators, expected outputs, and claim boundary before implementation proceeds. The execution-role record then states whether the selected registered role is used directly, narrowed by task overlay, or represented by a one-job provisional identity. Optional parent-child synthesis stays inside that same job; it does not create child AgentJobs or extra authority. Completion evidence must preserve validator results, generated outputs, fused-output paths when decomposition is used, and conflict status before it can pass. This keeps project-system repair reversible and auditable instead of becoming an informal repository rewrite.

Documentation impact is a receipt requirement, not a routing shortcut. A project-system job must either update the relevant source documentation or record why no update was needed, and the receipt must cover source docs, generated derivatives, classifier reason codes, and validators. Teaching-loop changes add the same burden for teaching packets, source specs, HTML, and GitHub-facing Markdown. The important boundary is mechanical: if live source changes or generated derivatives exist, the impact record must name them or explain the no-op. That makes documentation debt visible to future agents without letting a derivative page become a control contract or scientific authority.
Validator Chain

The validator chain checks bootstrap registration, source/hash metadata, Mermaid parity, emitted project-improvement signals, documentation-impact receipts, research-control records, diff boundaries, depth lint, and teaching-QA packet structure. Teaching-QA validation makes sure curated packets cite selected source materials, avoid generated-output authority, and preserve source gaps instead of inventing answers. Depth lint keeps source specs and rendered pages from collapsing into shallow renderer instructions. Research-control validation then checks the task, decision, job, execution-role record, completion, and checkpoint boundary. These checks do not make generated pages authoritative; they verify that derivative surfaces continue to follow their registered sources.
