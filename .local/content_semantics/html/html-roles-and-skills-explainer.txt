Summary of Roles and Skills
The roles-and-skills catalog is the active inventory of registered agent roles, historical role versions, task-local execution overlays, and repo-local skill front doors used by the project. Its function is to show which role contracts currently govern work, which roles are status-defined or superseded for audit history, which support subroles may ask or answer teaching-loop questions, which skills provide project-governed procedures, and which tools are merely operator-context aids. This matters because skills are useful only inside the right authority boundary: Documentation Curator v0.8.0 can maintain explanatory specs, teaching packets, GitHub-facing Markdown, and source-backed HTML; Documentation Student and Documentation Teacher support that loop without writing tracked docs; Project-Control Maintainer owns control contracts; Validator Engineer owns deterministic checks; and physics roles remain separate from documentation work. The catalog fits the overall system by giving maintainers a readable map from registry rows to role contracts and skill procedures before they execute a task.

Status-defined roles are registered enough to describe a protected boundary, but they are not general autonomous execution permission. Gate Chair authority is the clearest example: the role exists so the project can name promotion responsibility, yet a normal agent may not treat that status as permission to approve claims. A task overlay or one-job provisional role can narrow a role for a bounded job, but protected expansion still requires explicit gate evidence rather than convenience or repetition. This distinction matters for teaching work too. Student and Teacher are active support subroles, but they do not gain Curator write authority; their status and allowed behavior remain limited by the role registry and execution-role schema.

Global skills, browser tools, local shells, and editor automation can help the operator gather evidence, inspect rendered pages, run validators, or prepare a readable explanation. They do not become project authority unless the repository mirrors their contract into `.codex/skills/` and a bounded job allows the path. This prevents an operator convenience from silently becoming a workflow rule. For example, a browser can verify that an HTML derivative renders correctly, but the authority for what that page may claim remains in the registered source spec, role contract, registries, and validation receipts. Convenience can support a task; it cannot replace the role, source, registry, or validator boundary.

The boundary is practical: use tools to inspect, render, validate, and explain, then return authority to tracked sources and registries. Generated HTML, GitHub-facing Markdown, teaching packets, wiki notes, PDFs, and local caches orient readers, but they do not authorize physics claims, new permissions, or control behavior. This page is therefore a map, not a permission grant. Before selecting a role or writing a file, a maintainer should inspect the active role registry row, the current task or handoff, the task-local execution-role record, and the relevant source spec or canonical source file. The roles-and-skills catalog helps find those objects; it does not replace them.
