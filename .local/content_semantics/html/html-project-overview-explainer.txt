Project Overview
AEther-Flow is a dual research program: one lane tests a speculative Æther-flow interpretation against ordinary exact general relativity, and the other lane builds the agent-control machinery that keeps that research auditable.
Summary of Project Overview
AEther-Flow is organized around two coupled systems. The physics system keeps ordinary exact general relativity as the observable benchmark while treating any first-principles derivation from Æther or Æther-flow substrate structure as open until a gated source-side derivation succeeds. The AI research-agent system supplies the operating discipline: tracked state, Director decisions, bounded AgentJobs, role contracts, validators, registries, handoffs, and generated explanatory surfaces. The project needs both systems because speculative physics can drift into unsupported certainty unless every proposal, refutation, repair, and negative result remains source-bound and auditable. The overview functions as the entry map for that structure: physics terms route to ontology and claim gates; workflow questions route to research system, role routing, and research control; authority questions route to source authority, roles and skills, memory, and technical requirements.

Two-Lane Navigation

The navigation model starts with two practical questions. If a reader is asking what the project is trying to explain physically, the path runs through the Æther-flow ontology, exact-GR benchmark boundary, claim gates, and source authority. If the reader is asking how the work is controlled, the path runs through the research system, role routing, research-control validation, roles and skills, memory, and technical requirements. The atlas prevents directory order from becoming conceptual order. A newcomer can see that TeX, registries, Markdown specs, HTML, GitHub-facing pages, wiki notes, and local retrieval are not equal sources of truth; each has a role in the two-lane program.
Physics Research Lane
README.md
ontology/aether-and-aether-flow.md
registries/CLAIM_BOUNDARY_REGISTRY.csv
The physics lane explores whether an Æther-flow substrate can recover the observable structure already modeled by ordinary exact general relativity. The repository currently treats exact GR as the benchmark and the substrate derivation as unresolved. That distinction is central: ontology vocabulary may guide candidate construction, but it cannot replace the missing derivation of Lorentzian geometry, clocks, causal structure, same-metric matter coupling, invariance, and closure. Claim gates and source registries preserve this boundary so a useful conceptual model does not become an accepted theory by presentation quality, task completion, or repeated phrasing.
AI Research-Agent Lane
research_control/README.md
registries/AGENT_JOB_REGISTRY.csv
registries/DIRECTOR_DECISION_REGISTRY.csv
The AI research-agent lane is the project’s controlled workflow for doing difficult theoretical work with language-model agents. A request or handoff is resolved into a Director decision, one bounded AgentJob, a selected role or task overlay, explicit read and write paths, expected outputs, validators, completion records, and the next handoff. The system is not an autonomous proof engine. Its value is disciplined containment: it can draft, audit, refute, preserve obstructions, improve project machinery, and regenerate documentation while making authority boundaries visible before any result is trusted.
Authority and Memory Spine

Authority flows from registered sources and registries, not from convenience. Scientific claims live in registered TeX; routing, provenance, generated-output tracking, and agent-queryable memory live in CSV registries; front-door guidance and source specs live in registered Markdown; HTML, GitHub-facing Markdown, PDFs, wiki notes, and local retrieval surfaces help humans and agents read the project. The memory system makes this practical by recording object identities, hashes, relationships, generated outputs, and validation status. Retrieval can accelerate review, but it must always point back to the source row or canonical file.
Operator Path

An operator who changes project knowledge should inspect the relevant authority surface first, edit the registered source or registry row, regenerate derivatives, and run the validator chain required by the bounded task. Documentation changes normally start at a Markdown source spec or registered Markdown page, then render HTML and GitHub-facing derivatives, run teaching and depth checks when applicable, bootstrap memory/wiki/registry outputs, validate documentation impact, and check research-control boundaries. The technical-requirements drilldown separates mandatory project tooling from optional local aids so setup friction does not become a mistaken authority decision.
