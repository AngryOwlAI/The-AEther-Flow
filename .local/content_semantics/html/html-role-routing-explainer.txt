Role Routing
Role routing chooses the correct authority lane before an agent changes files or claims progress.
Summary of Role Routing
Role routing is the project’s decision system for assigning bounded work to the correct registered role or task-local execution overlay. Its function is to connect task state, Director decisions, base role contracts, provisional or overlay authority, and registry evidence so an agent knows who owns the change, what paths may be written, which validators are required, and when the job must stop. It also explains why optional parent-child synthesis is a decomposition of analytical perspective inside the selected AgentJob, not a new role class or permission expansion. The project needs role routing because physics roles, documentation roles, validator roles, memory roles, and project-control roles carry different authority. Collapsing them into one generic helper would risk claim promotion, direct derivative edits, or untracked control changes.

research_control/README.md
Role routing is the project’s way of choosing the right kind of helper before work begins. A physics obstruction, a documentation refresh, a validator repair, and a memory-system update are not the same job. Routing asks what authority class is needed, which registered role fits, whether the role can be used directly, whether a task overlay is needed, and which AgentJob will constrain the work. The plain rule is simple: select authority first, then act inside the selected boundary.
Why Routing Exists
AGENTS.md
registries/AGENT_ROLE_REGISTRY.csv
One smart helper would be convenient but unsafe. The repository contains science-bearing roles, documentation roles, validator roles, memory roles, project-system roles, and human-gated promotion authority. Each has different failure modes. A Documentation Curator can improve explanatory surfaces but cannot change a validator. A Project-Control Maintainer can change contracts but needs a bounded overlay for explanatory docs. A Gate Chair cannot be silently activated. Routing preserves those distinctions so capability does not become permission.
Key Terms
registries/AGENT_ROLE_REGISTRY.csv
registries/ROLE_EXECUTION_REGISTRY.csv
.agents/schemas/EXECUTION_ROLE_SCHEMA.md
A role is a reusable versioned contract. A role version records the exact active or historical contract. An execution-role record is the task-local binding for one AgentJob. A task overlay is a bounded one-job delta on a registered role. A one-job provisional role is temporary and non-reusable until registered. Parent-child synthesis adds analytical perspectives inside one AgentJob. A human gate protects authority expansions such as claim promotion, Gate Chair action, benchmark status, canonical ontology authority, or permanent role registration.
Routing Walkthrough
registries/DIRECTOR_DECISION_REGISTRY.csv
.agents/schemas/AGENT_JOB_SCHEMA.md
A routing walkthrough starts with the task request or handoff. The Director identifies the authority class, compares role candidates, selects one role and version, records rejected alternatives, sets claim boundaries, and points to an AgentJob. The AgentJob then lists allowed reads, writes, generated paths, validators, expected outputs, and stop conditions. The task-local role file records whether the role is direct, overlaid, or provisional. Only after that chain exists should implementation begin.
Common Questions
README.md
AGENTS.md
registries/DIRECTOR_DECISION_REGISTRY.csv
Who chooses the role? The Director decision selects it. Why not use one role for everything? Different jobs carry different authority and risk. What should be inspected? The role registry, Director decision row, AgentJob YAML, execution-role record, task-local role file, and completion receipt. Does decomposition create extra authority? No. Parent and child perspectives inherit the same AgentJob boundary and must resolve into one controlled output. The practical review habit is to follow the evidence chain from decision to job to role record to completion before trusting the result.
Examples and Non-Examples
research_control/README.md
.agents/schemas/EXECUTION_ROLE_SCHEMA.md
.agents/schemas/AGENT_JOB_SCHEMA.md
A valid example is a Documentation Curator job that updates a source spec, regenerates HTML, and records documentation impact. Another valid example is a Project-Control Maintainer overlay that updates a validator and matching docs inside one allowlist. Invalid examples include a generated HTML file granting a role new authority, a repeated provisional role becoming permanent without registration, a child perspective writing outside the parent AgentJob, or a documentation role silently promoting a physics claim.
Common Misunderstandings
AGENTS.md
.agents/schemas/EXECUTION_ROLE_SCHEMA.md
.agents/schemas/AGENT_JOB_SCHEMA.md
The first misunderstanding is that generated docs authorize behavior; they do not. The second is that provisional means permanent; it expires after the owning job unless registered. The third is that a task overlay is reusable policy; it is not. The fourth is that parent-child synthesis creates child AgentJobs; it creates internal perspectives inside one job. The fifth is that human gates are decorative; they protect authority expansions the agent cannot assume.
Authority Boundaries
AGENTS.md
research_control/README.md
.agents/schemas/ROLE_SCHEMA.md
Role routing does not authorize physics claim promotion, direct edits outside the allowlist, generated-output authority, protected expansions, or schema and validator changes by implication. It authorizes only the selected role, for the selected job, over the declared paths, with the declared validators. If the work needs a different authority class, the job must stop, route a new bounded project-system action, or request human-gated approval. If any needed permission is absent, the safe result is a new routed task or a controlled stop, not improvisation inside the current job.
Check Understanding
registries/AGENT_ROLE_REGISTRY.csv
registries/ROLE_EXECUTION_REGISTRY.csv
.agents/schemas/AGENT_JOB_SCHEMA.md
A reader can test understanding by asking five questions before accepting a task result. Which role was selected? Which execution-role record binds it? Which files could be written? Which validators were required and run? Which authority claims were explicitly forbidden? If any answer is missing, the routing evidence is incomplete. This retrieval practice makes role routing operational rather than decorative. The questions are intentionally mechanical because authority mistakes often happen when a reader accepts a fluent explanation without checking the task-local contract.
