Role Routing
Explain how the project decides which AI agent role executes a bounded task, how the execution-role contract constrains that role, and how routing avoids authority drift.
Summary of Role Routing
Role routing is the project's decision system for assigning bounded work to the correct registered role or task-local execution overlay. Its functionality is to connect task state, Director decisions, base role contracts, provisional or overlay authority, and registry evidence so an agent knows who owns the change, what paths may be written, which validators are required, and when the job must stop. It also explains why optional parent-child synthesis is a decomposition of analytical perspective inside the selected AgentJob, not a new role class or permission expansion. This matters because the repository contains physics roles, documentation roles, validator roles, memory roles, and project-control roles with different authority levels; collapsing them into one generic helper would risk claim promotion, direct derivative edits, or untracked control changes. Role routing fits the overall project by making authority selection itself auditable before implementation begins.

Role routing is the project desk that chooses the right kind of agent before implementation starts. A request is first classified by the kind of authority it touches: physics drafting, documentation, validation, memory maintenance, project-control repair, or another bounded lane. The Director decision then selects one role for one AgentJob. The execution-role record narrows that role to exact one-job semantics, including allowed writes, validators, expiry, and stop conditions. This keeps a helpful explanation from quietly becoming permission and keeps a useful helper from wandering into a lane it does not own.
Why This Exists
README.md
AGENTS.md
registries/AGENT_ROLE_REGISTRY.csv
The repository separates physics claims, AI-methodology claims, tooling claims, and human-facing explanations. One general helper would blur those boundaries. Documentation Curator can improve source-backed explainers, but it cannot change validators or role authority. Validator Engineer can edit deterministic checks, but it does not make human policy decisions. Gate Chair authority remains human-gated. Role routing is the mechanism that keeps those distinctions visible before work begins. Its value is not bureaucracy for its own sake; it is auditability, so a reviewer can see why one role was selected and why other roles were rejected.

Why cannot one helper do every task?
Different work carries different authority. A documentation update, validator repair, physics derivation attempt, and Gate Chair decision need different owners, outputs, validators, and gates.
Who chooses the selected role?
The Director decision records the selected role and the AgentJob that will use it. The decision row is part of the audit trail.
What should I inspect next?
Inspect the role registry, Director decision row, AgentJob YAML, task-local role record, execution-role registry row, and completion record. Generated explainers can orient you, but they do not authorize work.

Common Confusions

.agents/schemas/EXECUTION_ROLE_SCHEMA.md

Generated docs are not authority; they help readers find the source surfaces. A provisional role is not permanent; it expires after its owning AgentJob and cannot become reusable by habit. A task overlay is not a role rewrite; it is a task-local delta. Parent-child synthesis is not multiple AgentJobs; it is internal perspective synthesis under the same execution-role record. These repairs matter because authority drift often starts as a vocabulary mistake. The safest reader habit is to ask which source file, registry row, schema, job, or completion record actually carries the permission being described.

Role routing does not promote physics claims, alter canonical ontology, grant Gate Chair authority, change validator behavior, register permanent roles, or make generated outputs authoritative. Protected authority expansion requires a human gate. Generated HTML, GitHub-facing Markdown, wiki notes, PDFs, and local caches may be useful for orientation, but they cannot override source files, registries, schemas, role contracts, AgentJobs, or validator results. If an explanation sounds like permission, the logical next step is to inspect the task-local execution-role record and the AgentJob allowlist.

Overlay Provisional Boundary
AGENTS.md
README.md
research_control/README.md
research_control/AGENTS.md
There are four boundary forms. A registered role is reusable policy with a versioned contract. A task overlay temporarily changes authority for one known job while preserving the base role. A one-job provisional role handles an unusual bounded need and expires after the job. Parent-child decomposition is different: it creates internal analytical perspectives only after the selected AgentJob and execution-role record already exist. The matrix matters because flexibility without expiry becomes hidden policy. If the same provisional role pattern recurs, the project treats it as a project-system signal for possible registration rather than letting habit create authority. The legitimate claim is operational: routing records can explain why a role was allowed to do specific work. They cannot create scientific acceptance or edit outside the allowlist.
