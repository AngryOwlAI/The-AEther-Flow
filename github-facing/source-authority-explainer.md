# Source Authority And Generated Derivatives

The trust question in AEther-Flow is not "which page is clearest?" It is
"which source is allowed to define the project state for this claim?" A public
HTML page may be easier to read than a source file; a wiki note may be easier
to search than a registry; an Obsidian mirror may be convenient during local
work. None of those conveniences changes the authority hierarchy.

The operating discipline is source-first. Registered TeX carries physics and
derivational claims. Registries carry routing, provenance, generated-output
tracking, and agent-queryable memory metadata. Registered Markdown carries
front-door guidance, source specs, publication briefs, role and skill
contracts, and project-control notes. GitHub-facing Markdown, tracked HTML,
wiki notes, PDFs, semantic extracts, Obsidian mirrors, and `.local` caches are
downstream support surfaces.

Use generated surfaces for orientation, then follow their source paths. If a
generated derivative and a registered source disagree, the source wins and the
derivative needs repair. If no registered source supports the claim, the honest
answer is that the page cannot establish it.

## Authority Ladder

| Layer | What It Can Define | What It Cannot Do |
| --- | --- | --- |
| Registered TeX | Physics and derivational claims within their stated status. | Change workflow authority or bypass claim gates. |
| Registries | Routing, provenance, generated-output tracking, memory metadata, and source-object hashes. | Replace the source file whose row they describe. |
| Registered Markdown | Front-door guidance, scoped agent rules, publication briefs, source specs, roles, skills, schemas, and project-control notes. | Promote physics claims unless the lane explicitly owns them. |
| Generated reader surfaces | GitHub-facing Markdown, tracked HTML, wiki notes, indexes, and PDFs for orientation. | Define source authority or override canonical sources. |
| Local retrieval | Semantic extracts, Obsidian mirrors, SQLite indexes, and `.local` caches for search and preview. | Serve as tracked control state or citation authority. |

## Source-To-Derivative Boundary

| If the question is about... | Inspect first | Use derivatives for |
| --- | --- | --- |
| Physics status or derivation | Registered TeX and claim-boundary rows. | Plain-language orientation and navigation. |
| Task or routing authority | `research_control/` records and control registries. | Understanding the workflow shape. |
| Public explainer content | Publication brief and Markdown source spec. | Reading convenience after source binding is known. |
| Memory lookup or freshness | Registry rows and the project-memory skill contract. | Finding likely paths and stale retrieval warnings. |
| File inventory or local search | Source registry rows and tracked files. | Search acceleration, never final authority. |

## Status-Card V2 Authority Boundary

Status-card v2 reduces cognitive load; it does not create a new authority
layer. A public status card must still trace back to registered control
sources, the Distance-to-GR ledger, and row-specific evidence before it is
cited.

| Status-card field | Public use | Authority boundary |
| --- | --- | --- |
| Positive status | States the scoped status first so real progress is not hidden. | Cannot promote ontology, metric status, matter coupling, field equations, benchmark status, or completed derivation. |
| Exact scope | Names the source-side, finite/local, or blocked-target scope. | Cannot broaden the row beyond its registered source and ledger evidence. |
| Blocked overread | Names what the row does not establish. | Cannot turn scoped obstruction into global no-go or future impossibility. |
| Next burden | Names the next honest burden before stronger claims. | Cannot route work or issue a Gate Chair verdict without tracked control authority. |

## Source-First Checklist

1. Name the question: physics claim, workflow state, role authority,
   documentation quality, generated artifact, or local retrieval state.
2. Identify the source lane that owns that question.
3. Inspect the source file and the relevant registry row.
4. Use generated documentation only to navigate, explain, or review.
5. Preserve exact qualifiers such as `generated noncanonical`,
   `draft/control`, `source-only`, `local`, `exact-branch`, and
   `human-gated` when summarizing.

## Failure Modes

- Treating a clear HTML page as if it can promote a physics claim.
- Treating a wiki note or semantic extract as if it can override a registry
  row.
- Treating `.local` cache state as tracked control state.
- Treating a validator pass as a broad endorsement of scientific truth,
  editorial quality, role authority, or generated-output authority.
- Treating this trust map as a replacement for the registries it points to.

## Reader Scope

Reader scope: source-authority orientation only. This page cannot change the
hierarchy, replace a registry, promote ontology, certify a benchmark, issue a
Gate Chair verdict, expand roles, or modify routing behavior.

## Safe Operating Summary

Safe summary: Use generated and local surfaces to find the right source, then
inspect the registered source file and registry row before citing, editing, or
routing.

Unsafe summary: A generated page, wiki note, PDF, semantic extract, Obsidian
mirror, or `.local` cache can override the authority hierarchy.
