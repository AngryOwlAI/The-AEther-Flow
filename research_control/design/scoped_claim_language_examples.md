# Scoped Claim Language Examples

## Scope

This note gives local agents concrete examples for high-risk claim language
after the P2 scoped-positive vocabulary and current-frontier alias pilot. It is
project-control guidance only. It does not edit ontology, adopt a source law,
prove an unrestricted theorem, or promote matter coupling, Einstein equations,
benchmark status, or completed derivation.

Use these examples when writing task outputs, handoffs, current-frontier
summaries, validation receipts, or public-facing draft language that mentions
high-risk scoped-positive objects.

## Statement Forms

Use a two-part statement when space is limited:

```text
X is [scoped-positive status] for [declared source-side use]; it is not
[blocked downstream reading].
```

Use a three-tier statement when the distinction between status, non-status,
and next route must be explicit:

```text
Status: [what is established]. Non-status: [what is not established].
Next route: [what remains required before any stronger claim].
```

Use the four-layer statement from the scoped-positive vocabulary for the
highest-risk rows:

```text
Control status: [gate/control term]. Mathematical status: [actual formal
payload]. Physical status: [what is not established]. Promotion status:
[blocked or next lawful route].
```

## Examples

### 1. `M_src` Underclaiming

Bad wording:

```text
M_src is only tentative and has no positive status.
```

Why it is wrong: `M_src` has a real scoped-positive status as a source-only
object. Underclaiming it hides valid progress and makes later routing less
legible.

Correct wording:

```text
M_src is adopted_as_source_only_object under scoped source-only adoption; it
is not a target manifold, not a metric, and not a GR derivation.
```

Required source paths to inspect:

- `registries/DISTANCE_TO_GR_LEDGER.csv`
- `research_control/design/scoped_positive_claim_vocabulary.md`
- `research_control/design/distance_to_gr_status_aliases.yaml`
- `research_control/current_frontier.md`

Forbidden overread: Do not render `M_src` as `MetricData(E)`, `g_eff`, target
manifold adoption, matter coupling, Einstein equations, benchmark promotion,
or completed derivation.

Validator PASS means the checked control surfaces are structurally valid and
fresh under their validators; it is not proof of ontology, source law, matter
coupling, Einstein equations, benchmark status, or completed derivation.

- `AGENTS.md`

Forbidden overread: Do not cite validator PASS as proof authority, Gate Chair

### 11. Registry Row As Proof

Bad wording:

```text
The registry row proves the theorem.
```

Why it is wrong: registries route and preserve provenance. They are authority
for metadata and control state, not independent theorem proof.

Correct wording:

```text
The registry row records routing/provenance metadata for the cited object; any
scientific claim must be supported by the canonical source or tracked
completion named by that row and remains inside its claim boundary.
```

Required source paths to inspect:

- relevant row in `registries/*.csv`
- canonical source path named by the row
- relevant task completion or handoff
- `AGENTS.md`

Forbidden overread: Do not treat registry presence, a source hash, a commit,
or a role record as scientific proof or promotion authority.

### 12. Gate Chair Scoped Evidence Vs Adoption

Bad wording:

```text
The Gate Chair accepted the object, so it is adopted.
```

Why it is wrong: Gate Chair results are scoped to the exact reviewed question.
An evidence/precondition acceptance is not adoption unless the Gate Chair
verdict explicitly says adoption.

Correct wording:

```text
The Gate Chair accepted the object only as the scoped evidence/precondition
specified by the approval and handoff. Adoption remains false unless the
tracked Gate Chair verdict explicitly authorizes adoption for that object.
```

Required source paths to inspect:

- relevant approval under `research_control/approvals/`
- relevant Gate Chair task artifact
- latest handoff named by `research_control/program_state.yaml`
- `registries/CLAIM_BOUNDARY_REGISTRY.csv`

Forbidden overread: Do not broaden scoped evidence/precondition acceptance
into source-law adoption, object adoption, benchmark closure, or completed
derivation.

### 13. Generated Derivative Authority

Bad wording:

```text
The wiki note says the claim, so the claim is authoritative.
```

Why it is wrong: wiki notes, generated indexes, PDFs, HTML explainers,
semantic extracts, Obsidian notes, and `.local` caches are derivative or
retrieval layers. They do not override canonical sources or tracked control
state.

Correct wording:

```text
The generated derivative is reader or retrieval support only. Verify the claim
against the registered source, registry row, task completion, latest handoff,
and program state before using it.
```

Required source paths to inspect:

- `AGENTS.md`
- `research_control/AGENTS.md`
- relevant canonical source or registry row
- latest tracked handoff and completion

Forbidden overread: Do not use generated derivatives as independent authority,
proof surfaces, routing authority, or promotion authority.

### 14. Global Theory Rejection Overread

Bad wording:

```text
The frozen toy route rejects the whole theory.
```

Why it is wrong: a frozen-negative or scoped obstruction is local to stated
premises unless a separate global no-go theorem proves the stronger claim.

Correct wording:

```text
The route is frozen_negative_no_global_rejection or a scoped obstruction under
the stated premises. It does not reject all future source extensions or the
global theory.
```

Required source paths to inspect:

- `research_control/design/scoped_positive_claim_vocabulary.md`
- `research_control/current_frontier.md`
- relevant refuter completion record
- `registries/CLAIM_BOUNDARY_REGISTRY.csv`

Forbidden overread: Do not turn local obstruction, frozen-negative status, or
failed finite toy route into future source-extension impossibility, universal
no-go theorem, or global theory rejection.
