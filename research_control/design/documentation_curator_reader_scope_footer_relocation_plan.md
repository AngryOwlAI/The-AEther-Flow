# Documentation Curator Reader Scope Footer Relocation Plan

## Purpose

This modification plan defines a phased implementation path for moving the
visible `Reader scope` block in the GitHub-facing Markdown and tracked HTML
publication corpus from the opening area to the bottom of each page, directly
above the authority footer section.

This plan is a project-control design note. It does not edit public explainer
outputs, source specs, generated HTML, registries, validators, role contracts,
schemas, science sources, or physics claims in this transaction.

## Recommendation

Move the `Reader scope` block to a stable bottom-of-page position while
preserving the existing authority boundary language exactly unless a source
inspection proves a wording repair is required.

Target Markdown structure:

```markdown
# Page Title

Subject-specific opening.

Main reader sections.

## Reader Scope

Reader scope: ...

<!-- explainer-control: authority_footer -->

## Source Binding And Authority
```

Target HTML structure:

```html
<section class="reader-scope" data-explainer-control="reader_scope" aria-labelledby="reader-scope-title">
  <h2 id="reader-scope-title">Reader Scope</h2>
  <p>Reader scope: ...</p>
</section>
</main>

<footer data-explainer-control="authority_footer">
```

The opening may keep a short subject label or status chip, but the full
`Reader scope` explanatory boundary should not remain in the hero, header, or
first explanatory section after a page is revised.

## Authority Boundary

The relocation is a presentation change. It must not:

- promote generated Markdown or HTML into source authority;
- change physics status, ontology status, benchmark status, claim gates, or
  Gate Chair authority;
- alter role authority, routing behavior, schemas, validators, checkpoint
  behavior, or task allowlists except in an explicitly approved validator
  guardrail phase;
- weaken source-path visibility or the generated noncanonical warning; or
- hand-edit generated wiki notes, generated registries, PDFs, or `.local`
  retrieval caches.

Tracked HTML remains a generated noncanonical derivative. Direct HTML-only
repair remains blocked when the corresponding source spec, GitHub-facing page,
registry row, review evidence, or generation convention also needs to change.

## Evidence Inspected

Current repository inspection found:

- `registries/PUBLICATION_BRIEF_REGISTRY.csv` lists 17 reviewed publication
  pages with GitHub-facing Markdown and tracked HTML outputs.
- All 17 tracked HTML pages contain an `authority_footer` footer hook and a
  visible top-positioned `Reader scope` block.
- All 17 GitHub-facing Markdown pages contain the authority footer marker.
- 15 GitHub-facing Markdown pages still contain a top-positioned
  `Reader scope` paragraph; `project-overview` and `source-authority` already
  use the footer-style Markdown authority block and have no separate top
  `Reader scope` paragraph.
- `research_control/design/github_facing_explainer_contract.md` and
  `research_control/design/html_explainer_flexible_presentation_contract.md`
  already define footer authority placement for the full generated
  noncanonical paragraph.
- `scripts/validate_publication_process.py` and
  `scripts/project_control/audit_documentation_surfaces.py` currently guard
  generated-noncanonical authority footer placement. A future guardrail may
  also reject top-positioned `Reader scope` blocks after relocation.

Memory preflight was used only for navigation. It reported known local
retrieval freshness warnings and identified the existing post-migration quality
plan as relevant source context; canonical repository files were inspected
directly before this plan was written.

## Phase 0: Baseline Audit

Goal: confirm exact relocation work before editing the corpus.

Tasks:

- Create a new bounded research-control task for the implementation packet.
- Run memory preflight and inspect the publication brief registry.
- Inventory all current `Reader scope` occurrences in `github-facing/` and
  `html/`.
- Record, per page, the current opening position, footer hook position, exact
  boundary text, source spec path, GitHub-facing path, HTML path, and whether
  the Markdown page already satisfies the target structure.
- Decide whether each page needs a prose move only, source-spec wording repair,
  HTML layout repair, nav update, CSS update, screenshot refresh, or validator
  guardrail.

Exit criterion:

- A page-by-page audit artifact exists and identifies the precise files for
  Phase 1 through Phase 5.

## Phase 1: Pattern And Guardrail

Goal: lock the implementation pattern before repeated edits.

Tasks:

- Confirm the bottom placement convention:
  - Markdown `## Reader Scope` immediately before
    `<!-- explainer-control: authority_footer -->`.
  - HTML `section[data-explainer-control="reader_scope"]` immediately before
    the authority footer.
- If required, update the GitHub-facing and HTML contracts to name the
  `reader_scope` hook explicitly.
- If strict regression prevention is approved, update
  `scripts/validate_publication_process.py` and
  `scripts/project_control/audit_documentation_surfaces.py` so pages with the
  new hook cannot keep a duplicate top-positioned `Reader scope` block.
- Add narrow tests or fixture evidence only if validator behavior changes.

Exit criterion:

- One target pattern is documented and mechanically checkable before page
  migration begins.

## Phase 2: Pilot Pair

Pages:

- `project-overview`
- `source-authority`

Reasoning:

These pages already satisfy the target Markdown authority-footer pattern, so
they are the safest pilot for moving the HTML `Reader scope` block from the
header to the bottom position above the footer.

Tasks:

- Move the HTML `Reader scope` block below the final main content section and
  above `<footer data-explainer-control="authority_footer">`.
- Preserve exact boundary wording unless source inspection requires a correction.
- Verify that mobile and desktop layout still present the scope block clearly.
- Capture pilot screenshots and review notes.

Exit criterion:

- The pilot proves the target HTML pattern without changing page authority,
  source basis, or physics/control claims.

## Phase 3: Physics Status And Claim-Boundary Pages

Pages:

- `aether-flow-physics-program`
- `exact-gr-benchmark-boundary`
- `aether-flow-ontology`
- `gr-derivation-roadmap`
- `claim-gates`

Reasoning:

These pages carry the highest public overclaim risk. Their `Reader scope`
language must remain visible and exact while moving out of the opening area.

Tasks:

- Move each GitHub-facing Markdown `Reader scope` paragraph to `## Reader
  Scope` directly above the authority footer marker.
- Move each HTML `Reader scope` block to the bottom section above the authority
  footer.
- Preserve qualifiers such as `draft/control`, `source-only`, `local`,
  `exact-branch`, `source-extension data`, and `human-gated` wherever they
  appear.
- Confirm no page implies completed derivation, ontology promotion, benchmark
  promotion, or Gate Chair approval.

Exit criterion:

- All five pages keep their boundary language but no longer lead with the
  `Reader scope` section.

## Stop Conditions

Pause implementation if:

- a relocation would require changing canonical TeX, ontology, benchmark,
  derivation, or claim-gate status;
- a page loses its source materials, generated noncanonical paragraph, or
  authority footer;
- a direct HTML edit is not synchronized with the relevant source spec,
  GitHub-facing page, review evidence, and registry support;
- validator or audit changes are needed but not explicitly included in the
  active phase;
- screenshots reveal unreadable footer flow, mobile overflow, or overlapping
  sections; or
- any required validation command fails.

## Can It Be Improved?

An improvement will be to add a narrow mechanical guard after the first pilot:
detect `Reader scope:` before the first major content section in Markdown or
inside an HTML `header`, and reject it once a page declares the
`reader_scope` bottom hook. This is reversible, testable, and prevents the
corpus from drifting back toward top-heavy authority warnings.

A different perspective will be to treat `Reader scope` as a reader contract
rather than a warning. The bottom placement can work as a final boundary check:
the reader first learns the subject, then sees the exact limits before source
binding and authority metadata.
