# DDR-20260718-013: Pin accepted relay reasoning effort in v4

## Objective and evidence

Implement the direct user request as a new bounded project-control transaction.
The current task metadata was read directly from the Codex task and reported
`model: gpt-5.6-sol` with `reasoning_effort: max`. Live task-tool discovery
showed that `create_thread` exposes `thinking` and that `gpt-5.6-sol` supports
`max`. No relay goal, successor task, or external mutation was created.

The completed v3 task tree `RT-20260718-012` hashes to
`4a70356a7fbb89e32847fdaae111ad7a8ae33c1eb235f311c996070334baf526`
and remains unchanged.

## Decision

Adopt `continue-research-goal.v4` as the only mutable goal-record version.
Require combined pre-launch acceptance of the exact goal and selected effort,
default the in-memory launcher candidate to `max`, preserve either candidate
when only the other is edited, and create no state on ambiguous approval.

After acceptance, the launcher must prove active-model support and exact
current-task metadata equality. Every created relay task receives the persisted
effort through `create_thread.thinking`; the model argument remains omitted.
The recursive worker repeats the metadata check before claim and rediscovers
`create_thread` support before successor reservation.

The helper stores an immutable discussion contract binding the accepted goal
hash, reasoning effort, and confirmation marker. Its hash is linked from
initialization evidence, the generation-1 route, and read-only summaries.
V1-v3 records remain validation-and-summary-only without migration or automatic
resumption.

## Role-fit decision

deliberately split across two skills, one schema reference, one state helper,
focused tests, and a registered policy receipt. Validator Engineer and
Process-Integrity Auditor functions are represented by the focused suite and
