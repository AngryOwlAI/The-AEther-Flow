Roles And Skills

Roles define who may do project work; skills define governed procedures for doing that work inside the repository.

Summary of Roles and Skills

The roles-and-skills catalog is the active inventory of registered agent roles, historical role versions, task-local execution overlays, and repo-local skill front doors used by AEther-Flow. Its function is to show which role contracts currently govern work, which roles are status-defined or superseded for audit history, which support subroles may ask or answer teaching-loop questions, which skills provide project-governed procedures, and which tools are merely operator-context aids. This matters because skill availability is not project authority. Documentation Curator v0.9.0 owns subject-first explanatory specs, teaching packets, GitHub-facing Markdown, and source-backed HTML; Student and Teacher support the teaching loop without writing tracked docs; Project-Control Maintainer owns control contracts; Validator Engineer owns deterministic checks; physics roles remain separate from documentation and project-system work.

Active Roles

registries/AGENT_ROLE_REGISTRY.csv.agents/roles/research_ops/documentation-curator.v0.9.0.md

Active roles are the current operating surface. Director of Research and Project-System Director select bounded work. Project-Control Maintainer changes control contracts when authorized. Documentation Curator v0.9.0 writes subject-first explanatory documentation and regenerated derivatives. Documentation Student asks learner questions, and Documentation Teacher answers from selected sources inside that loop. Validator Engineer, Memory-System Maintainer, and Process-Integrity Auditor support checks and project machinery. Physics roles such as Ontology Formalizer, Candidate Constructor, Refuter, and Smuggling Auditor operate in the science lane under their own boundaries.

Status-Defined Roles

registries/AGENT_ROLE_REGISTRY.csv.agents/roles/physics/gate-chair.v0.1.0.md

Status-defined roles are known but not freely executable. Gate Chair authority is the important example: it is associated with promotion or rejection decisions and therefore requires explicit human-gated authorization. A role can be defined in the registry without being available for routine autonomous use. This protects scientific status decisions from being triggered by convenience, strong wording, or tool availability. A maintainer should treat status-defined authority as visible vocabulary for review, not as a callable tool available during ordinary continuation.

Superseded Roles

registries/AGENT_ROLE_REGISTRY.csvregistries/ROLE_EXECUTION_REGISTRY.csv

Superseded roles remain useful for audit history. Old Documentation Curator versions, for example, explain why older AgentJobs had the permissions and validator expectations they had. Superseded does not mean active. A future task should use the active role version unless an execution record is being audited historically. Keeping old contracts visible lets the project explain past work without reactivating obsolete authority. This is especially important when a validator or explainer changed after an older job, because the old receipt must be judged against the contract active at that time.

Role-Skill Evidence

registries/AGENT_ROLE_REGISTRY.csv.agents/schemas/EXECUTION_ROLE_SCHEMA.md

Role-skill relationships must be evidence-labeled. A role contract, skill contract, task overlay, or registry row can declare that a skill is required or appropriate. Inferred support tools can help an operator, but they should be labeled as support rather than project authority. The distinction matters when a powerful external tool could edit files but the selected role cannot. Evidence keeps the project from confusing capability with permission. When evidence is missing, the safest description is “operator aid” or “likely support,” followed by a new bounded project-system task if the relationship should become contract authority.

Support Tools

AGENTS.mdregistries/MARKDOWN_SOURCE_REGISTRY.csv

External plugins, browser automation, shell commands, global Codex skills, and operator-local helpers can be useful for reading, testing, or rendering. They do not become project contract authority unless mirrored into the repository and routed through the appropriate role or task boundary. A support tool may gather context, run a validator, or inspect a browser screenshot; it may not expand a role, change a claim, or override registries. This boundary lets the project benefit from a rich local environment while keeping reproducible project behavior inside tracked contracts.

Operator Boundary

AGENTS.mdresearch_control/README.md

The operator context boundary separates what the local environment can do from what the project authorizes. A shared terminal, editor, browser, or plugin may make work faster, but the repository authority remains in source files, registries, task records, role contracts, and validator receipts. Before using a convenience tool to write project knowledge, the operator should confirm the selected role, AgentJob allowlist, source class, and validation chain. The same rule applies to AI assistants: model ability, plugin availability, and shell access do not expand the active AgentJob.
