Summary of Documentation Curator Teaching Loop

The Documentation Curator teaching loop is the project's method for making source-backed explainers easier to understand without weakening authority boundaries. The Curator chooses a subject and source bundle, then uses a Documentation Student to ask plain reader-centered questions and a Documentation Teacher to answer those questions inside the declared source bundle. The Curator reviews the exchange, writes or updates a curated Teaching Q&A packet, and distills that packet into the Markdown source spec, GitHub-facing Markdown, and tracked human-only HTML derivative. The loop is subject-first: it must explain what the project component does, why the project needs it, how it works, what it can and cannot claim, and where a reader should go next. It does not let generated pages, teaching packets, Student questions, or Teacher answers become independent authority.

Source-Backed Coverage

Curator Authority

.agents/roles/research_ops/documentation-curator.v0.9.0.md.codex/skills/html-visual-explainer/SKILL.mdresearch_control/design/github_facing_explainer_contract.md

The Curator owns the tracked documentation outputs in the loop. It may update explanatory Markdown, Markdown source specs, curated teaching packets, GitHub-facing Markdown, source-backed HTML derivatives, documentation registries, and documentation-impact records when the AgentJob allows those paths. That ownership is narrower than it may first appear. The Curator cannot change physics claims, role contracts, schemas, validators, routing behavior, or generated-output authority. Its subject-first rule keeps explanations focused on the project component's function, value, sources, boundary, and next reading path instead of turning documentation into metadata about itself.

Student Questions And Teacher Answers

.agents/roles/research_ops/documentation-student.v0.1.0.md.agents/roles/research_ops/documentation-teacher.v0.1.0.md.agents/roles/research_ops/documentation-curator.v0.9.0.md

The Student and Teacher are support subroles. The Student asks reader-centered questions about purpose, operation, examples, non-examples, boundaries, confusing terms, and next steps. The Teacher answers those questions plainly, adds a technical anchor, names source paths, marks source gaps, and adds boundary notes when authority or claim status is involved. Neither support role writes tracked documentation. This division is important: reader confusion is allowed to shape the final explanation, but the source bundle and Curator review decide what can be carried into registered project artifacts.

Teaching Q&A Packet

.agents/schemas/TEACHING_QA_PACKET_SCHEMA.mdscripts/validate_teaching_qa.pymarkdown/teaching-packets/project-overview.teaching-qa.mdmarkdown/teaching-packets/role-routing.teaching-qa.md

The curated packet records the teaching exchange in a structured way. It declares packet identity, topic, source spec, derived outputs, audience model, roles, rounds, source materials, claim boundary, and authority status. Its body contains Curator feature selection, two rounds of Student questions, two rounds of Teacher answers, and synthesis notes. Those notes must name concepts for HTML and GitHub-facing Markdown, glossary candidates, common confusions, examples, next readings, source gaps, and claims intentionally not made. The validator exists so packets remain source-bound support rather than free-form authority.

Derivative Synchronization

.codex/skills/aether-teaching-explainer/SKILL.md.codex/skills/html-visual-explainer/SKILL.mdresearch_control/design/github_facing_explainer_contract.md

After synthesis, the Curator distills teaching content into the Markdown source spec, GitHub-facing Markdown, and tracked HTML. The source spec remains the backing surface for the HTML derivative, while the GitHub-facing page gives humans and external AI a readable orientation layer. Both are noncanonical for physics and control decisions. This synchronization pattern is useful because it gives the project multiple reading surfaces without multiplying authority. A reader can start from a friendly page, but any claim about source status, role behavior, validator requirements, or routing must trace back to the declared source materials.

Advisory Format Boundary

.agents/roles/research_ops/documentation-curator.v0.9.0.md.codex/skills/html-visual-explainer/SKILL.mdscripts/validate_teaching_qa.py

Renderer and lint scripts provide useful quality gates: they check required fields, source evidence, summary placement, teaching packet shape, depth, and derivative consistency. They do not decide which project functionality deserves coverage or what the final explanation should emphasize. That decision belongs to the Curator inside the AgentJob boundary and source bundle. The practical rule is balanced: pass the validators, but do not let a template replace subject-first judgment. A well-formed page that omits a major project function is still incomplete documentation.
