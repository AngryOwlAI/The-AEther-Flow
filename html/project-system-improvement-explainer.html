Project-System Improvement Loop

How documentation drift, control drift, validator gaps, memory issues, and routing ambiguity become bounded project-system work.

Generated noncanonical reader surface. This page explains existing controls; it does not create signals, resolve signals, change validators, alter routing, expand role authority, or authorize physics claim promotion.

Signal To AgentJob Flow

Observe State

Start with tracked state: current Git diff, registered open signals, memory preflight, and inspected canonical sources.

Classify

The classifier script identifies documentation-impact and project-system reason codes.

Resolve

The resolver script compares current diff work with registered signals and recommends one boundary.

Execute One Job

The selected role executes one bounded AgentJob with explicit write paths, source classes, outputs, and stop conditions.

Record Evidence

Completion, documentation-impact receipt, checks, and signal-resolution fields preserve the transaction.

Classifier, Resolver, Checkpoint Gate

Surface Question answered Boundary
classify_project_changes.py Does the current Git diff require documentation impact or project-system routing? Classification evidence only. It does not prove the change is correct.
resolve_project_improvement.py Which open signal or current diff should be handled as the next bounded project-system step? Advisory routing state. It is not a hard checkpoint gate by itself.
Checkpoint checks Are changed paths allowed, required records present, and deterministic checks passing? Blocking comes from failed checks or concrete authority-boundary violations.

Signal Registries

Type Registry

registries/PROJECT_IMPROVEMENT_SIGNAL_TYPE_REGISTRY.csv defines the allowed signal vocabulary and default recommended routing metadata.

Examples include documentation drift, control contract drift, validator gaps, memory retrieval failure, routing ambiguity, and claim-boundary confusion.

Instance Registry

registries/PROJECT_IMPROVEMENT_SIGNAL_REGISTRY.csv records concrete signals with task, job, role, severity, status, evidence, and resolution fields.

High and critical open signals take priority. Low and medium signals remain backlog unless no current project-system action is pending.

Evidence Checklist

One bounded AgentJob

The objective, allowlist, source classes, forbidden paths, outputs, and claim boundary define the actual work.

Documentation impact

Every state-changing project-system AgentJob needs research_control/tasks/<task_id>/documentation_impact.yaml.

Signal closure

Resolved, completed, or closed signals need resolved_by_job_id, resolution_evidence_path, and resolved_at.

For a successful signal resolution, the evidence path must point to a completion YAML with validation_status: "PASS" and a matching job_id. A rejected signal may instead cite a Director decision that names the signal and explains the rejection.

Failure Modes

  • Closing a signal without PASS completion evidence or a rejection decision.
  • Using free-text signal language without a concrete registry row.
  • Treating resolver output as a hard checkpoint gate by itself.
  • Omitting documentation-impact receipts for state-changing project-system jobs.
  • Promoting generated HTML, wiki notes, Obsidian notes, semantic extracts, or .local caches to authority.
  • Using project-system improvement to alter physics claim status.
