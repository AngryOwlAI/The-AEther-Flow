Summary of Project-System Improvement

Project-system improvement is the repair lane for the research machinery itself. It covers documentation drift, role and schema contracts, validator behavior, memory tooling, generated-document pipelines, trigger logic, signal routing, and operational reliability. The workflow begins with source inspection and a structural classifier, then uses an advisory resolver and signal registries to decide whether one bounded AgentJob is needed. A Documentation Curator job handles explanatory documentation drift; a Project-Control Maintainer or other project-system role handles contracts, validators, schemas, or control behavior. Every state-changing project-system AgentJob must record documentation impact, regenerate the source-first memory surfaces when needed, and pass research-control validation. The loop exists so the system can improve itself without turning maintenance work into physics continuation or claim promotion.

Source-Backed Coverage

Classifier And Resolver

.codex/skills/improve-project-system/SKILL.mdscripts/project_control/classify_project_changes.pyscripts/project_control/resolve_project_improvement.pyresearch_control/README.md

The classifier gives the transaction a structural description of changed paths and reason codes. It helps decide whether the work affects documentation, generated derivatives, registries, contracts, validators, or control state. The resolver then reports advisory routing state. That advisory output is useful, but it is not a hard checkpoint blocker by itself. The hard blockers are concrete validator failures and authority-boundary violations. This split lets the project notice future work without preventing a coherent current transaction from completing after the required validations pass.

Project-Improvement Signals

.codex/skills/improve-project-system/SKILL.mdregistries/PROJECT_IMPROVEMENT_SIGNAL_TYPE_REGISTRY.csvregistries/PROJECT_IMPROVEMENT_SIGNAL_REGISTRY.csvscripts/project_control/collect_project_improvement_signals.py

Project-improvement signals make recurring or emitted system concerns queryable instead of leaving them as free text. Signal types live in the type registry, while concrete signal instances live in the signal registry with severity and terminal-state evidence. A signal that moves out of the backlog needs a resolving job, evidence path, and timestamp. Multiple signals may close in one job only when the job names each signal and the completion lists the same resolved set. This structure prevents maintenance concerns from being silently lost after a completion or handoff mentions them.

One Bounded AgentJob

AGENTS.mdresearch_control/README.md.codex/skills/improve-project-system/SKILL.md

The improvement lane keeps the one-job discipline. Explanatory documentation drift routes to Documentation Curator; skill, role, schema, control-registry, or validator drift routes to Project-Control Maintainer or a more specific project-system role; system-design or validation drift may route to director, validator, or memory roles. The selected job defines allowed reads, writes, outputs, validators, claim boundaries, and stop conditions. This keeps project repair reversible and auditable. It also prevents a documentation task from quietly changing control behavior or a validator task from becoming an open-ended rewrite.

Documentation Impact

research_control/README.md.codex/skills/improve-project-system/SKILL.mdscripts/project_control/validate_documentation_impact.py

Documentation impact is a receipt requirement for state-changing project-system work. The record covers changed source paths, generated derivatives, classifier reason codes, source surfaces inspected, updated docs, registry changes, validators run, and no-update rationale when applicable. The point is mechanical traceability: future agents should know whether the transaction changed how humans or agents understand, operate, validate, route, or extend the system. A source documentation edit may be enough for plain documentation work outside a project-system AgentJob, but every state-changing project-system AgentJob needs the explicit impact record.

Checkpoint Boundary

.codex/skills/improve-project-system/SKILL.mdresearch_control/README.mdAGENTS.md

The checkpoint boundary is conservative. The transaction regenerates memory and registry derivatives when needed, validates emitted signals, validates documentation impact, validates research-control state, and runs diff checks. It stops when a required edit would touch canonical ontology, science drafts, generated wiki notes, PDFs, generated sidecars, or paths outside the job allowlist. It also stops when a Documentation Curator job would change contracts or routing behavior. This keeps project-system improvement useful without letting maintenance work override the source-first authority hierarchy.
